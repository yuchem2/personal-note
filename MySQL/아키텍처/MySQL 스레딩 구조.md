> 해당 문서의 내용은 MySQL 서버가 전통적으로 가지고 있는 스레드 모델이며, 커뮤니티 에디션에서 사용되는 모델이다. 엔터프라이즈의 경우 전통적인 스레드 모델과 함께 [스레드 풀](스레드%20풀.md)을 사용할 수도 있다. 
> - 전통적인 스레드 모델: 커넥션 별로 포그라운드가 하나씩 생성되고 할당
> - 스레드 풀 모델: 커넥션과 포그라운드 스레드는 1:1 관계가 아니라 하나의 스레드가 여러 개의 커넥션을 전담

MySQL 서버는 프로세스가 아니라 스레드 기반으로 동작한다. 이 스레드는 Foreground Thread와 Background Thread로 구분할 수 있다. MySQL 서버에서 실행 중인 스레드의 목록은 `performance_schema` 데이터베이스의 `threads` 테이블을 통해 확인할 수 있다.

```sql
SELECT * FROM performance_schema.threads;
```
## 포그라운드 스레드
최소한 MySQL 서버에 접속된 클라이언트 수만큼 존재한다. 주로 각 클라이언트가 요청하는 **쿼리 문장을 처리한다.** 커넥션이 종료되면 해당 포그라운드 스레드는 *스레드 캐시*로 되돌아간다. 

만약 이때 스레드 캐시에 일정 개수 이상의 대기 중인 스레드가 있으면 스레드 캐시에 넣지 않고 스레드를 종료시켜 일정 개수의 스레드만 존재하도록 한다. (최대 스레드 개수는 `thread_cache_size`로 조절한다.)

포그라운드의 주된 역할을 다음과 같다.
- MySQL의 데이터 버퍼나 캐시에서 데이터를 읽는다.
- 직접 디스크의 데이터나 인덱스 파일로부터 데이터를 읽는다.

[MyISAM 스토리지 엔진](MyISAM%20스토리지%20엔진.md) 테이블은 디스크 쓰기 작업까지 포그라운드 스레드가 처리하지만, [InnoDB 스토리지 엔진](InnoDB%20스토리지%20엔진.md) 테이블은 데이터 버퍼나 캐시까지만 포그라운드 스레드가 처리하고, 나머지 작업은 백그라운드 스레드가 처리한다.
## 백그라운드 스레드
[MyISAM 스토리지 엔진](MyISAM%20스토리지%20엔진.md)의 경우는 해당 사항이 거의 없지만 [InnoDB 스토리지 엔진](InnoDB%20스토리지%20엔진.md)은 다음과 같은 작업을 백그라운드로 처리한다.
- Insert Buffer를 병합
- 로그를 디스크로 기록
- InnoDB 버퍼 풀의 데이터를 디스크에 기록
- 데이터를 디스크에서 버퍼로 기록
- 잠금이나 데드락을 모니터링

위 작업 모두 중요하지만 가장 중요한 것은 Log Thread와 Write Thread(버퍼의 데이터를 디스크로 내려쓰는 작업 수행)이다. MySQL 5.5부터 데이터 읽기/쓰기 스레드를 각각 2개 이상 지정할 수 있게 되었으며 이를 `innodb_write_io_threads`와 `innodb_read_io_threads` 시스템 변수로 개수를 설정한다. (하지만 데이터 읽기 작업은 주로 포그라운드에서 수행된다.)

> 사용자의 읽기를 처리하는 도중 쓰기 작업은 지연되어 처리될 수 있지만 데이터 읽기는 절대 지연될 수 없다. 그래서 일반적인 상용 DBMS에는 대부분의 쓰기 작업을 버퍼링해서 일괄 처리하는 기능이 탑재되어 있다. InnoDB 또한 그렇다. 하지만 MyISAM은 그렇지 않고 사용자 스레드가 쓰기 작업까지 함께 처리한다. (그래서 버퍼링이 되지 않는다.)
