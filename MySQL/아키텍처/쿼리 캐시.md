SQL의 실행 결과를 메모리에 캐시하고, 동일한 SQL 쿼리가 실행되면 테이블을 읽지 않고 즉시 결과를 반환한다. 이를 통해 매우 빠른 성능을 보였다. 그러나 테이블의 데이터가 변경되면 캐시에 저장된 결과 중 변경된 테이블에 관련된 것들을 모두 삭제해야 했다. 이로 인해 동시 처리 성능 저하가 발생했다. 결국 **MySQL 8.0에서는 쿼리 캐시가 서버 기능에서 완전히 제거됐다.**
## 동작 원리
쿼리 캐시는 SQL 문장의 의미를 분석하여 저장하지 않고, 입력된 SQL 문자열 자체를 Key, 실행 결과를 Value로 하는 메모리 Map 구조로 동작한다. 

1. 클라이언트의 쿼리 요청
2. SQL Hashing Check -> Cache Hit -> 메모리에서 즉시 반환
3. Cache Miss -> [쿼리 실행 구조](쿼리%20실행%20구조.md)에 따라 결과 생성
4. 결과를 클라이언트에 반환하고, 쿼리 캐시 Map에 저장

입력된 문자열 자체를 Key로 하기 때문에 대소문자, 공백, 줄바꿈, 주석 하나라도 다르면 다른 키로 인식하여 Cache Miss가 발생한다.
- `SELECT * FROM users WHERE id = 1;`
- `select * from users where id = 1;` (Cache Miss)
- `SELECT * FROM users WHERE id = 1 ;` (Cache Miss)

모든 `SELECT` 명령이 캐시되는 것이 아니라 다음과 같은 캐시 불가 조건에 해당하는 구문이 있는 경우 캐시가 동작하지 않는다.
- 동적/시계열 함수 사용: `UUID()`, `NOW()`, `RAND()`, `SYSDATE()` 등
- 사용자 정의 변수/임시 테이블/서브 쿼리 일부
- 권한 제어: 로그인한 유저의 테이블/칼럼 접근 권한 확인이 별도로 필요한 경우

만약 캐시된 결과에 해당하는 테이블에 `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` 등 데이터/구조 변경이 발생하면 해당 테이블에 관련된 모든 쿼리 캐시 항목을 탐색하여 일괄 삭제한다. 
## 사용법(MySQL 8.0 이전)
[설정 파일](설정%20파일.md)에 다음과 같은 항목을 추가하면 쿼리 캐시를 사용할 수 있다. 

```toml
[mysqld]
# 쿼리 캐시 활성화 방식 설정
# 0 (OFF)    : 사용 안 함
# 1 (ON)     : SQL_NO_CACHE를 제외한 모든 SELECT 캐시
# 2 (DEMAND) : SQL_CACHE를 명시한 SELECT 쿼리만 캐시
query_cache_type = 1

# 쿼리 캐시에 할당할 전체 메모리 크기 (0이면 비활성화)
query_cache_size = 64M

# 단일 쿼리당 캐시할 수 있는 최대 결과 크기 (대용량 ResultSet 캐싱 방지)
query_cache_limit = 2M
```

쿼리 레벨은 다음 명령어로 제어할 수 있다.

```sql
# `query_cache_type = 1 (ON)` 환경에서 특정 쿼리 캐시 제외
SELECT SQL_NO_CACHE * FROM orders WHERE created_at >= NOW();
# `query_cache_type = 2 (DEMAND)` 환경에서 특정 쿼리만 캐시 명시
SELECT SQL_CACHE * FROM categories WHERE status = 'ACTIVE';
```
## MySQL 8.0 이후 쿼리 캐시 전략
MySQL 8.0에서 쿼리 캐시가 완전히 제거된 후, 쿼리 캐싱의 목적(디스크 I/O 최소화 및 응답 속도 향상)은 **아키텍처의 서로 다른 계층으로 분산**되어 처리된다.
- Application Cache (Redis/Memcached)
    - 실제 쿼리 캐시가 담당하던 쿼리 결과 집합 저장 역할을 Redis 같은 전용 인메모리 데이터스토어로 이관하여 수행. DB 서버의 CPU/메모리 자원을 캐싱에 뺏기지 않으며 테이블 전체 무효화가 아닌, 특정 Key 단위로 세분화된 TTL및 캐시 정책 구현이 가능하다.
- [MySQL 엔진](MySQL%20엔진.md): Prepared Statement / Optimizer Hint
    - 쿼리 결과가 아닌 쿼리 분석/파싱/최적화 과정을 재사용하여 CPU 연산 부담을 줄임. 
    ```sql
    PREPARE stmt1 FROM 'SELECT * FROM users WHERE id = ?';
    SET @id = 1;
    EXECUTE stmt1 USING @id;
    ```
- [스토리지 엔진](스토리지%20엔진.md): InnoDB 버퍼 풀
    - 쿼리 결과 대신 디스크의 데이터/인덱스 블록을 메모리의 Buffer Pool에 올려두어, 동일한 데이터 접근 시 디스크 I/O 없이 메모리 상에서 쿼리를 처리함. 데이터가 일부 변경되더라도 테이블의 전체 캐시가 날아가는 것이 아니라, **변경된 더티 페이지만 백그라운드로 디스크에 기록되므로 쓰기 작업 시 전역 락 병목이 발생하지 않음**
