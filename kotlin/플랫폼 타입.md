코틀린이 널 관련 정보를 알 수 없는 타입을 말한다. 그 타입을 [널이 될 수 있는 타입](널이%20될%20수%20있는%20타입.md)으로 처리해도 되고 널이 될 수 없는 타입으로 처리해도 된다. 즉, 이는 자바와 마찬가지로 플랫폼 타입에 대해 수행하는 모든 연산에 대한 책임은 개발자에게 있다는 의미다. 컴파일러는 모든 연산을 허용한다.

> **왜 플랫폼 타입을 도입했는가?**
> 모든 타입을 널이 될 수 있는 타입으로 다루는 경우 컴파일러가 널 가능성을 판단하지 못하므로 결코 널이 될 수 없는 값에 대해서도 `null` 검사가 필요하다. 특히 제네릭을 다룰 때 모든 원소에 대해 접근할 때마다 `null` 검사를 하거나 안전한 캐스트를 수행해야 한다. 이러한 이유에 따라 *개발자에게 책임을 부여하는 접근 방식을 택했다.*

```kotlin
val i: Int = person.name
// ERROR: Type mismatch: inferred type is String! but Int was expected
```

코틀린에서는 따로 플랫폼 타입을 선언할 수 없다. 자바 코드에서 가져온 타입만 플랫폼 타입이 된다. 하지만 IDE나 컴파일러 오류 메시지에서는 플랫폼 타입을 볼 수도 있다. `String!`은 코틀린 컴파일러와 IDE에서 자바 코드에서 온 프랫폼 타입을 표기하는 방법이다. 이런 표기를 직접 코드에서 사용할 수 없다. `!` 표기는 `String!` 타입의 널 가능성에 대해 아무 정보도 없다는 사실을 강조할 뿐이다.

```kotlin
// java 코드
interface StringProcessor {
    void process(String value);
}

// kotlin 코드
class StringPrinter : StringProcessor {
    override fun process(value: String) {
        println(value)
    }
}

class NullableStringPrinter : StringProcessor {
    override fun process(value: String?) {
        if (value != null) {
            println(value)
        }
    }
}

```

또한 자바 메서드를 오버라이드할 때 그 메서드의 파라미터와 반환 타입을 [널이 될 수 있는 타입](널이%20될%20수%20있는%20타입.md)으로 선언할지 널이 될 수 없는 타입으로 선언할지 결정해야 한다. 컴파일러는 위 두 선언을 모두 받아들인다.
