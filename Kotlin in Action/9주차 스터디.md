## 질문 리뷰
- 코틀린에서 스케쥴러가 코루틴을 실행시키고, 코루틴의 내부 객체로 정보를 관리하는 것으로 받아들여졌는데, 스케쥴러가 각 코투린의 종료 시점의 위치나 정보를 직접적으로 관리하나요?
    - 스케쥴러 관리를 Dispather가 관리하며 코루틴의 모든 것을 관리함 = JS 이벤트 루프가 하는 모든 역할을 한다고 생각하면 편함
        - 스케줄러는 코루틴 내부의 구체적인 데이터나 "얘가 몇 번째 줄까지 실행되다 왔는지" 같은 사생활에는 일절 관심이 없습니다. 오직 자기 앞에 있는 일감 큐(Queue)에서 `Continuation` 객체를 꺼내어, **"너는 `Dispatchers.IO` 풀에 있는 2번 스레드로 가서 일해!"** 하고 물리 스레드에 던져주는 매칭 역할만 수행합니다.
        - 코루틴이 실행되다가 `suspend`를 만나면, 코틀린 컴파일러는 현재까지의 로컬 변수 상태와 다음에 실행해야 할 코드의 위치(컴파일러가 매긴 번호인 `label`)를 `Continuation` 객체 내부의 멤버 변수로 완전히 박제(상태 저장)해 버립니다.
- 일시정지할 수 있다고 했는데, 스레드가 어떻게 중단하는 것으로 동작하는건가?
    - 스레드가 중단되는 것은 아님. Job이 중단되는 것
    - Job이 어떻게 중단되는걸까? 
    - 일반적인 동시성 처리는 작업을 하다 기다리는 비용이 많은 부분을 만났을 때 OS 기반에서 CPU 점유 권한을 다른 프로세스/스레드로 컨텍스트 스위칭
    - 위와 같은 작업이 매우 무겁고, 오래걸리기 때문에 이를 추상화한 개념이 고루틴(Go 언어), 코루틴 등과 같은 개념.
    - 코루틴에서는 컨텍스트 스위칭을 하는 것이 하니라 해당 작업을 만났을 때 작업을 일시정지하고, 해당 위치를 저장한 뒤 다른 작업에게 맡김. 다른 작업도 반복하다가.. 해당 작업의 차례가 됬고, 일시정지된 작업이 완료된 경우 다시 되돌려준다. (동시성만족)
    - 위 작업에서 여러 스레드를 왔다갔다 하면 결국 병렬 + 동시성을 만족
    - **코루틴:** 결국 일감 '객체'일 뿐이라서, 기반 스레드가 블로킹되어 OS에 의해 CPU 점유권을 빼앗기면 **그 스레드에 얹혀있던 모든 코루틴 Job들이 한꺼번에 얼어붙는다.** (웹 서버에서 전통 동기식 라이브러리와 썼을 때 위험한 이유)
    - **가상 스레드:** 그 자체가 JVM이 인식하는 '스레드'이기 때문에, 내부에서 블로킹이 일어나도 물리 스레드가 OS에 CPU 권한을 넘기지 않고 **JVM 스케줄러가 다른 가상 스레드에게 바로 토스해 버린다.**

## 추후 공부
- **Kotlin Coroutine - Thread Pinning**
    - _내용:_ 개발자가 `suspend` 대신 구형 동기식 블로킹 코드를 짰을 때, 캐리어 스레드가 통째로 굳어버려 대기 큐의 다른 Job들까지 연쇄 살인당하는 메커니즘 분석.
- **Java Virtual Thread - Platform Thread Pinning** -> JDK 24에서 문제를 해결
    - _내용:_ `synchronized` 키워드나 JNI 호출 시 가상 스레드가 가상 머신(JVM) 레벨에서 풀리지 않고 박혀버리는 한계와, 자바 진영이 이를 `ReentrantLock` 등으로 어떻게 엔진 레벨에서 메꿔가고 있는지 분석.
- **네이티브 메서드 (JNI) 호출 시 피닝:** 자바 코드가 아니라, C언어나 C++로 작성된 OS 네이티브 라이브러리(`정밀 암호화 알고리즘`, `일부OS 로우레벨 파일 시스템 제어` 등)를 자바 내부에서 호출하여 그 안에서 대기(Blocking)가 걸리는 경우는 **여전히 물리 스레드가 피닝됩니다.** 이 부분은 JVM 엔진이 통제할 수 없는 자바 외부의 영역이기 때문입니다.
